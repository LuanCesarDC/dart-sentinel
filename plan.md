# Dart Sentinel — Roadmap

**The static analysis layer that makes LLM-generated Dart/Flutter code maintainable.**

Dart Sentinel is a static analysis tool with a singular focus: ensuring that code — whether written by a developer or generated by an LLM — is deterministically correct according to your project's architecture, conventions, and quality standards. You define the rules once in `analyzer.yaml`; Sentinel enforces them without ambiguity.

> **Install globally:** `dart pub global activate dart_sentinel`
> Do NOT add `dart_sentinel` to your `pubspec.yaml` — it's a dev tool, not a project dependency.

### The Problem

- **LLMs generate structurally plausible but architecturally wrong code.** They ignore layer boundaries, create circular dependencies, produce god classes, skip tests, and duplicate logic. Without a machine-verifiable ruleset, every AI session degrades the codebase slightly.
- **Skills and custom instructions alone are not enough.** LLMs hallucinate, forget long-context rules, and can't reason about the full import graph. Telling an LLM "respect the architecture" in a system prompt is probabilistic. Sentinel is deterministic.
- **Traditional linters focus on style, not structure.** `dart analyze` won't tell you that a feature is importing from another feature, that a layer is violating the dependency DAG, or that a class has no reachable test.
- **New developers (human or AI)** make structural mistakes because they don't know the conventions yet.

### The Solution

Define your architecture and principles **once** in a YAML config. Dart Sentinel enforces them on every run — and integrates into your AI workflow so LLMs can self-correct:

1. **Deterministic enforcement loop for LLMs**: AI generates code → `dart_sentinel` runs → output fed back to the AI with exact violations → AI fixes → loop closes. No need to keep architecture constraints in the AI context window.
2. **MCP integration**: AI agents (Copilot, Cursor, Claude) call Sentinel directly via MCP — analyze, check imports, get architecture, compute blast radius, generate test scaffolds.
3. **IDE quick fixes**: Architecture-aware code generation (model boilerplate, test scaffolds) delivered as quick fixes — no build_runner, no annotations, no code generation step.
4. **Architecture refactoring**: Change the rules in `analyzer.yaml` → run the tool → get a deterministic list of everything that needs to change.
5. **Onboarding**: New developers get immediate feedback on architectural violations, not just style issues.

### Core Differentiators vs Other Tools

| | Dart Sentinel | DCL / DCM | Standard Dart Linter |
|---|---|---|---|
| **Architecture enforcement** | Layer deps, feature isolation, banned imports, import cycles | Partial (banned imports only) | None |
| **AI-friendly output** | JSON/Markdown reports consumable by AI agents | Console/JSON | IDE only |
| **MCP integration** | 10 tools via MCP — AI agents call sentinel directly | None | None |
| **Testing enforcement** | Untested files, test quality, coverage thresholds | None | None |
| **Deterministic rules** | Architecture defined in YAML, not in context | Rules are code-level only | Rules are code-level only |
| **Metrics & lint** | Core metrics + high-value lint rules + AI slop detection | 478 rules, 22 metrics | ~200 style rules |

> **Stack**: Pure Dart, using `package:analyzer` for AST parsing.
> **Execution**: `dart run dart_sentinel [options]`

## Phase 10 — Testing Enforcement

> **Goal**: Ensure AI-generated code comes with tests. When an AI agent creates `auth_service.dart`, it should also create the test. Dart Sentinel enforces this deterministically — detect missing tests, validate test quality, and enforce coverage thresholds.

### 10.1 `untested-files` rule

Detects files in `lib/` that have no corresponding test file.

```yaml
rules:
  untested_files: warning

testing:
  test_dir: test                    # default
  convention: suffix                # user_service.dart → user_service_test.dart
  exclude:
    - "**/*.g.dart"
    - "**/barrel.dart"
    - "lib/src/models/**"
  require_for:                      # optional: enforce only for specific paths
    - "lib/src/services/**"
    - "lib/src/rules/**"
```

**Output:**
```
⚠ untested-files: lib/src/services/auth_service.dart has no corresponding test file
  Expected: test/src/services/auth_service_test.dart
```

- [ ] Map lib/ files to test/ files using naming convention
- [ ] Support `suffix` convention (`_test.dart`) and custom patterns
- [ ] `exclude` patterns for generated files, barrels, simple models
- [ ] `require_for` to enforce only on critical paths
- [ ] Category: `testing`

### 10.2 `test-coverage-threshold` rule

Reads `lcov.info` from `dart test --coverage` and fails if coverage is below threshold.

```yaml
testing:
  coverage:
    file: coverage/lcov.info        # path to lcov.info
    global_min: 60                   # % minimum global coverage
    per_file_min: 40                 # % minimum per file
    exclude:
      - "**/*.g.dart"
    enforce_for:                     # per-path overrides
      - "lib/src/rules/**": 80
      - "lib/src/core/**": 70
```

**Output:**
```
✖ test-coverage: Global coverage 45% is below minimum 60%
⚠ test-coverage: lib/src/rules/dead_files_rule.dart has 0% coverage (min: 80%)
```

- [ ] Parse lcov.info format (DA: lines, LF/LH counts)
- [ ] Compute per-file and global coverage percentages
- [ ] Apply `enforce_for` path-specific thresholds
- [ ] Integrates with ratchet — coverage can only go up
- [ ] Category: `testing`

### 10.3 `test-quality` rule

Analyzes test files themselves for anti-patterns.

| Check | What it detects |
|-------|----------------|
| **empty-test** | `test('name', () {})` — test body with no assertions |
| **no-assertion** | Test that executes code but has no `expect()`, `verify()`, `throwsA()` |
| **test-too-long** | Test with >50 lines (suggest splitting) |
| **duplicate-test-name** | Two tests with the same name in the same file |
| **skipped-test** | `test('...', skip: ...)` or commented-out tests |
| **broad-matcher** | `expect(result, isNotNull)` instead of validating the actual value |

```
⚠ test-quality: test/auth_test.dart:15 — test 'login success' has no assertions
⚠ test-quality: test/auth_test.dart:30 — test 'handles error' is skipped
```

- [ ] Scan test files for `test()`, `testWidgets()` calls
- [ ] Check body for assertion calls (expect, verify, throwsA, expectLater, etc.)
- [ ] Detect `skip:` parameter and commented-out test bodies
- [ ] Configurable thresholds (test line limit)
- [ ] Category: `testing`

## Phase 17 — Model Code Generation via Quick Fixes

> **Goal**: Eliminate build_runner for model boilerplate. Any class inside a path declared as `models` in `analyzer.yaml` gets a quick fix that generates `toMap`/`fromMap`, `copyWith`, `==`/`hashCode`, and `toString` — all method names fully configurable, no annotations required.

This is the Dart Sentinel answer to Freezed: you don't annotate classes, you declare the intent in the architecture config (`this path contains models`), and the IDE quick fix generates the code on demand. Re-running it regenerates in place (idempotent). Works for plain Dart and Firestore projects equally.

### 17.1 Configuration

```yaml
models:
  # Any class inside these paths is eligible for model quick fix
  paths:
    - "lib/src/models/**"
    - "lib/src/domain/entities/**"
    - "lib/src/data/dtos/**"

  generate:
    to_map: toMap          # rename to toFirestore, toJson, etc.
    from_map: fromMap      # rename to fromFirestore, fromJson, etc.
    copy_with: copyWith
    equality: true         # generates == and hashCode
    to_string: true        # generates toString()

  serialization: map       # map | json | firestore
  # map     → Map<String, dynamic>
  # json    → same but method is toJson/fromJson
  # firestore → toFirestore()/fromFirestore(), handles Timestamp, DocumentReference

  immutable: true          # enforce that all fields are final (lint warning if not)

  exclude_from_copy_with: []   # field names to skip in copyWith
  exclude_from_serialization: []  # field names to skip in toMap/fromMap
```

### 17.2 `model-missing-methods` lint rule

Detects model classes that are missing any of the configured methods. Raises a warning — and the quick fix generates what's missing.

```
⚠ model-missing-methods: lib/src/models/user.dart:5
  UserModel is in a models path but is missing: copyWith, toMap, fromMap
  Quick fix available: Generate model methods
```

- [ ] New rule `model-missing-methods` (category: `models`)
- [ ] Detect classes in paths matching `models.paths` glob patterns
- [ ] Check for presence of each configured method name in the class AST
- [ ] Report one issue per class with the list of missing methods
- [ ] Configurable severity: `warning` by default

## Cut from Roadmap

The following items were evaluated and **removed** because they don't align with the project's core mission (architecture enforcement + AI slop detection + AI agent integration) or have better alternatives:

| Feature | Reason for cutting |
|---------|-------------------|
| **Halstead Volume / Maintainability Index** | Academic metrics with near-zero practical ROI. CC + LOC + nesting already cover what matters. No developer makes decisions based on Halstead Volume. |
| **Technical Debt calculation ($$$)** | Converting issues to USD/hours is imprecise theater. The ratchet system (already implemented) is more honest: "issues can only decrease, never increase." |
| **Duplicate Code Detection** | Complex to implement well (AST normalization, hashing, similarity thresholds), infinite edge cases. Dedicated tools (CPD, jscpd) already do this. Feature isolation + dead files catch the symptoms. |
| **HTML Report** | VS Code extension + MCP + JSON report already serve all audiences. Building a self-contained HTML dashboard (CSS/JS/charts) is high effort for a niche use case. Anyone can process the JSON. |
| **CI output formats** (Code Climate, Checkstyle, SonarQube) | Too niche. JSON is universal. Teams using SonarQube already have their own toolchain. Not worth maintaining 4 extra formatters. |
| **Widget metrics** (widget count, nesting level) | build-complexity already covers this indirectly (LOC + branches in build). Counting widget instantiations and nesting depth adds noise, not signal. |
| **Package-specific rules** (Bloc, Provider, Riverpod, GetIt) | Each framework has its own linter (bloc_lint, riverpod_lint). Competing where others already specialize is a losing strategy. Dart Sentinel's edge is architecture, not framework rules. |
| **Exports completeness check** | Edge case. Few codebases need to validate that barrel files export every declaration from subdirectories. |
| **Dependency graph .dot export** | Already replaced by Mermaid diagram generation in DependencyMapper. Mermaid is more portable (renders in GitHub, VS Code, etc.) and doesn't require Graphviz. |

## Tech Decisions

| Decision | Choice | Reason |
|----------|--------|--------|
| Language | Dart | Already has package:analyzer, zero extra dependency |
| Parser | package:analyzer (AST) | Already a dev dependency, precise analysis |
| Config | YAML (analyzer.yaml) | Consistent with ecosystem conventions |
| Output | Console + JSON + Markdown + Mermaid | Console for dev, JSON for CI, MD for PR, Mermaid for graphs |
| AI integration | MCP (Model Context Protocol) | Standard protocol, works with Copilot, Cursor, Claude Desktop |
| Distribution | `dart pub global activate` — NOT as pubspec dependency | Avoids analyzer version conflicts; this is a dev tool |
| Execution | `dart_sentinel` (global binary) | Clean CLI, no `dart run` prefix needed |
| Tests | test/ | Test rules with .dart snippets |
| Architecture | Rule engine + Issue model | Extensible, testable, isolated |
| Performance | Sequential now, cache/isolates when needed | ~500-800 files does not justify extra complexity yet |
| VS Code | TypeScript extension reading JSON report | Decoupled from Dart analysis, instant feedback |
| Model generation | Quick fix, no annotations, no build_runner | Intent declared in YAML config, not in class annotations |
